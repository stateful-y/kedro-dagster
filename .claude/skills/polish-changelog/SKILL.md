# Polish Changelog

git-cliff rewrites nothing. Every changelog bullet **is** the conventional-commit subject line with a PR link and author glued on. Subjects are written for maintainers reading `git log`, not for people reading a release, so entries are often locally true but externally opaque ("Correct the '0 unlinked' invariant", "Fix the fan-out bug"). This skill rewrites each new entry's **description** to be minimal and understandable — and touches nothing else.

It runs **after** git-cliff (mechanical) and **before** the release PR merges. The PR diff is the human review surface; this skill stops at pushing to that branch. It never merges.

```text
git tag pushed → changelog workflow → git-cliff → release PR opened
                                                        │
                                                  ★ polish-changelog: rewrite descriptions → commit → push
                                                        │
                                                  human reviews the PR diff → merge
```

## The scope boundary (read this first)

git-cliff owns the scaffold. You own the free-text description of each bullet — everything after the bullet's `-` marker and before its `([#` link — and, where the linked PR justifies it, which declared section that bullet belongs under. Everything else is immutable:

```text
## [0.29.4] - 2026-07-23                     ← IMMUTABLE  version header
This **patch release** includes 3 commits.   ← IMMUTABLE  hardcoded count — a desync landmine
### Features                                 ← IMMUTABLE  group heading = conventional-commit type
- Render numpydoc References ... as a list  ([#216](...)) by @gtauzin
  └──────────── EDITABLE ───────────┘  └──── IMMUTABLE: link + author, byte-for-byte ────┘
### Contributors ...                         ← IMMUTABLE
<!-- generated by git-cliff -->              ← IMMUTABLE
```

**Hard invariants — verify all of these before you push:**

1. **No entry may be dropped.** Every commit git-cliff emitted stays represented by at least one bullet. One-to-many is allowed when a commit genuinely spans sections; each derived bullet keeps the same PR link and `by @user` suffix byte-for-byte.
2. **Sections come from the project's `commit_parsers`.** Only headings declared in `.git-cliff.toml` may be used, rendered in the order of their `<!-- N -->` sort prefixes, with bullets oldest-first inside each — exactly what git-cliff would have emitted had the commit type matched the content.
3. **Re-sectioning must be grounded**, under the same rule as rewording: place a bullet from the linked PR's body or diff, or leave it where git-cliff put it. A section you cannot justify from the PR is a section you do not create.
4. **Links and `by @user` suffixes are byte-identical** to git-cliff's output.
5. **Only the newly-added top section changes.** git-cliff `--prepend` adds only the latest release; older sections were polished in their own PRs. Leave all previously released sections untouched.
6. **The `includes N commit(s)` line counts COMMITS, not bullets.** It stays as git-cliff wrote it. Splitting one commit into three bullets does not change how many commits the release contains, so the line remains true and must not be "corrected" to match a new bullet count.

**Why re-sectioning is allowed at all.** git-cliff groups by the *commit type prefix*, not by what the commit did. In a fleet where routine work lands as `chore(template): sync to vX.Y.Z`, the prefix carries almost no information: one such commit can contain security hardening, docs fixes and a refactor, and all of it lands under `### Miscellaneous Tasks`. A `### Security` section — the one a reader most wants to find — stays invisible because the subject matched `^chore` and nothing else.

Rewording alone cannot fix that. The best in-place rewrite of `Sync to v0.35.0` is still a changelog about the template, not about this package.

## Procedure

### 1. Find and check out the release PR

If you are already on the release branch, use it. Otherwise:

```bash
gh pr list --state open --json number,headRefName,title \
  --search "chore(release): update CHANGELOG.md in:title"
# or match the branch prefix:
gh pr list --state open --json number,headRefName --jq '.[] | select(.headRefName | startswith("changelog-v"))'
gh pr checkout <number>
```

### 2. Isolate the new section

Read only the block the PR added — the top release section in `CHANGELOG.md`:

```bash
git diff origin/main...HEAD -- CHANGELOG.md   # the added lines are the new section
```

Everything you edit lives in that block. Do not open older sections.

### 3. Rewrite each description — grounded, or leave it

For each bullet, get the real context from its linked PR (the subject line rarely carries it):

```bash
gh pr view <N> --json title,body,files --jq '{title, body, files: [.files[].path]}'
```

Rewrite the description from that evidence, following the style contract below. **If the PR's title/body/diff does not support a clearer wording that is still accurate, keep the original subject unchanged.** A plausible-but-wrong rewrite reads clean and can claim behavior the code does not have — abstaining is the correct default under uncertainty. Never assert an effect you cannot see in the PR.

### 4. Style contract

Each description is:

- **Capitalized imperative present**, matching git-cliff's `upper_first` — "Render", "Correct", "Drop", "Add", "Fix".
- **One line**, roughly ≤ 80 characters, no second sentence.
- **No trailing period.**
- **The user-visible effect over the internal mechanism**, when they differ.
- **Self-contained** — no repo-internal codenames ("the fan-out"), no undefined invariants, nothing that needs `git log` to understand.
- **Never provenance alone.** See the rule below.

| Before (git-cliff, verbatim subject) | After |
|---|---|
| Correct the See Also '0 unlinked' invariant | Fix the See Also section dropping entries that had no cross-reference |
| Correct three v0.29.0 rendering bugs the fan-out surfaced | Fix three docs-rendering regressions from v0.29.0 |
| Drop the stale 'yohou documents pre-commit' claim | Remove an outdated note about pre-commit from the docs |
| Render numpydoc References sections as a markdown list | *(already clear — leave unchanged)* |

#### A description must name a change, never just a version

`Update from template v0.39.0` is not a changelog entry. It names a *source* and a *version number* and says nothing about what the release did to this package — a reader learns strictly less than from the version header they are already looking at. The same failure wears other clothes: `Sync to v0.36.0`, `Bump the pinned toolchain`, `Apply the fan-out`, `Update dependencies`.

**The rule:** the description says what landed *in this package*. Where the source matters for traceability, it goes at the end in parentheses as provenance — never as the subject.

| Before | After |
|---|---|
| Update from template v0.39.0 | Fix three release-pipeline defects (template v0.39.0) |
| Update from template v0.38.0 | Add a CLAUDE.md project-instructions file for AI assistants (template v0.38.0) |
| Sync to v0.35.0 | Restrict workflow permissions and add secret scanning (template v0.35.0) |
| Update from template v0.40.1 | Fix a shell injection in the release publish job (template v0.40.1) |

Two traps this rule closes:

- **Normalising toward the uninformative.** When several template-update bullets appear together it is tempting to give them one consistent phrasing — and the phrasing they already share is the empty one. Consistency is worth having in the *shape* (effect first, provenance in parens), never in the content.
- **A parenthetical is not a description.** `Update from template v0.36.0 (Codecov OIDC + scorecard pin)` looks polished because it carries real information, but it still leads with the non-event. Promote the parenthetical to the subject and demote the version.

If the linked PR genuinely does not say what changed for this package, that is a grounding failure, not a licence to write the version number: say what the diff shows (`Update pinned CI action digests`) and no more.

### 5. Self-verify, then deliver

Before committing, confirm every hard invariant above. A word-level diff makes it obvious that only description text moved:

```bash
git diff --word-diff -- CHANGELOG.md   # descriptions and section placement may change; links, authors and the count line must not
```

Then commit and push to the PR branch — **do not merge**:

```bash
git commit -am "chore(changelog): polish release notes for vX.Y.Z"
git push
```

The maintainer reviews the polished diff on the PR and merges it.

## Out of scope

- **Whitespace / mechanical formatting** — owned by the git-cliff config, not this skill.
- **Historical sections** — only the new release section is ever touched.
- **Inventing headings** — only sections declared in the project's `.git-cliff.toml` `commit_parsers` may be used. Links, authors, the commit count and the footer stay git-cliff's, verbatim.
- **Dropping or merging entries** — one-to-many is allowed, many-to-one is not.
